# POST /lurv — создание листа учёта рабочего времени

Документация метода HTTP-сервиса `MCPService` расширения **ЛУРВ_HTTP** (версия API **1.0.1**).

## Таймауты

| Операция | Рекомендуемый timeout HTTP-клиента |
|----------|-----------------------------------|
| `GET /version`, запросы, чтение | 30 с (`read_timeout_sec`) |
| `POST /lurv`, `POST /document/{name}` | **120 с** (`create_timeout_sec`) |

Значения возвращает `GET /version`. В ответах создания документа также есть заголовок `X-MCP-Create-Timeout-Sec`.

## Назначение

Метод создаёт документ `эсЛистУчетаРабочегоВремени` (ЛУРВ) **с типовым заполнением**, как при интерактивном создании на форме, а не через универсальный `POST /document/{name}`.

Отличия от универсального метода:

- автоматический выбор **договора** при указании контрагента;
- заполнение флагов НДС и стоимости из договора;
- расчёт строк табличной части **Работы** по виду работы (номенклатура, место, выезды, суммы);
- расчёт **количества часов** из интервала времени;
- установка оценок СМК и резервного копирования из констант;
- присоединение файлов через БСП (`РаботаСФайлами`).

Документ **записывается без проведения** (`РежимЗаписиДокумента.Запись`).

## Эндпоинт

| Параметр | Значение |
|----------|----------|
| Метод | `POST` |
| URL | `/mcp-lurv/lurv` |
| Корневой URL сервиса | `mcp-lurv` (см. публикацию HTTP-сервиса в ИБ) |
| Content-Type | `application/json` |
| Обработчик | `ЛУРВPOST` |
| Исходный код | `Extent/ЛУРВ_HTTP/HTTPServices/LURV_HTTP/Ext/Module.bsl` |

## Общая схема работы (оркестратор)

```
1. resolve_lurv_contractor  → POST /lurv/resolve/contractor
2. resolve_lurv_work_type   → POST /lurv/resolve/work-type
3. resolve_lurv_employee    → POST /lurv/resolve/employee   (опционально)
4. get_lurv_by_number       → GET  /lurv/{number}   (сценарий «по аналогии с №…»)
5. create_lurv              → POST /lurv
```

| MCP tool | HTTP | Назначение |
|----------|------|------------|
| `resolve_lurv_contractor` | `POST /lurv/resolve/contractor` | Уточнить `contractor_ref` |
| `resolve_lurv_work_type` | `POST /lurv/resolve/work-type` | Уточнить `work_type_ref` |
| `resolve_lurv_employee` | `POST /lurv/resolve/employee` | Уточнить `employee_ref` (`Справочник.ФизическиеЛица`) |
| `get_lurv_by_number` | `GET /lurv/{number}` | Образец ЛУРВ для копирования |
| `create_lurv` | `POST /lurv` | Создание документа |

Поиск по фрагменту: Ё→Е, верхний регистр, слова (не-буквы — разделители) через `%` в шаблоне `ПОДОБНО`.

### POST /lurv/resolve/contractor

Тело: `{ "search": "Рамонти", "inn": null, "limit": 5 }` — обязателен `search` **или** `inn`.

| HTTP | status | Когда |
|------|--------|-------|
| 200 | `found` | Один кандидат: `ref`, `name`, `inn` |
| 200 | `ambiguous` | Несколько: `error: ambiguous_contractor`, `candidates[]` |
| 404 | `not_found` | `error: contractor_not_found` |

### POST /lurv/resolve/work-type

Тело: `{ "search": "разработка внешних отчетов", "contractor_ref": null, "limit": 5 }`.

Сначала справочник `эсВидыРаботСотрудников`, при пустом результате — по истории ТЧ `Работы` ЛУРВ (с дедупликацией по ref). Опциональный `contractor_ref` сужает историю.

Ответы: `found` / `ambiguous` + `candidates` / `not_found` (`work_type_not_found`). При `ambiguous` — **HTTP 200** (не 409).

### POST /lurv/resolve/employee

Тело: `{ "search": "Зиборова", "limit": 5 }`.

Поиск по `Справочник.ФизическиеЛица` (поля Наименование, ФИО, Фамилия, Имя, Отчество). Ответы: `found` / `ambiguous` (`employee_not_found` / `ambiguous_employee`) — как у контрагента.

### GET /lurv/{number}

Пример ответа 200:

```json
{
  "number": "00000019775",
  "contractor_ref": "uuid",
  "date": "2026-04-16T18:23:11",
  "comment": "",
  "works": [
    {
      "work_type_ref": "uuid",
      "work_type_name": "Работа в ТС",
      "time_start": "13:00:00",
      "time_end": "14:00:00",
      "hours": 1.0,
      "description": "…",
      "date": "2026-04-16"
    }
  ]
}
```

Даты и время — ISO 8601 (`XMLСтрока` / `yyyy-MM-dd` / `HH:mm:ss`). 404: `{ "error": "lurv_not_found", "number": "…" }`.

## Общая схема POST /lurv

```
Клиент → POST /lurv (JSON)
    │
    ├─► Поиск контрагента (ИНН / наименование / contractor_ref)
    │       ├─ 0 совпадений → 404
    │       ├─ >1 совпадений → 409 + candidates[]
    │       └─ 1 совпадение → продолжение
    │
    ├─► Создание документа + значения по умолчанию (организация, сотрудник текущего пользователя, валюта…)
    ├─► Установка контрагента → типовое заполнение договора и партнёра
    ├─► Сотрудник: `employee_ref` / `employee.name` переопределяет значение по умолчанию (не путать с `Ответственный`)
    ├─► Флаги по договору (НДС, стоимость, вид цены)
    ├─► Оценки СМК / РК из констант
    │
    ├─► Для каждой строки works[]:
    │       ├─ инициализация как на форме (замечания, цены по договору…)
    │       ├─ поиск вида работы (наименование / work_type_ref)
    │       ├─ заполнение даты, времени, описания; `Замечания` = «Замечаний нет»
    │       └─ типовой расчёт строки (номенклатура, часы, суммы)
    │
    ├─► Лист учёта сдан = Истина, ДатаСдачи, Закрыть задания (если включено в константе)
    ├─► Запись документа (без проведения)
    ├─► Присоединение files[] (описание = сводка всех description из works)
    │
    └─► 200 + ref, number, contract_ref, …
```

## Тело запроса

### Структура JSON

```json
{
  "date": "2025-06-19T10:00:00",
  "contractor": {
    "inn": "7701234567",
    "name": "ООО Ромашка"
  },
  "contractor_ref": "uuid-контрагента",
  "employee_ref": "uuid-физлица",
  "employee": { "name": "Зиборова" },
  "works": [
    {
      "date": "2025-06-18",
      "time_start": "09:00:00",
      "time_end": "11:30:00",
      "hours": 2.5,
      "work_type": "Консультация",
      "work_type_ref": "uuid-вида-работы",
      "description": "Настройка обмена"
    }
  ],
  "files": [
    {
      "name": "scan.pdf",
      "content_base64": "JVBERi0xLjQK..."
    }
  ],
  "comment": "Комментарий к документу"
}
```

### Поля шапки

| Поле | Обязательность | Описание |
|------|----------------|----------|
| `works` | **обязательно** | Массив работ; не может быть пустым |
| `contractor` | условно | Объект с `inn` и/или `name` для поиска контрагента |
| `contractor_ref` | условно | UUID ссылки на контрагента; приоритетнее поиска; используется после ответа 409 |
| `organization_ref` | нет | UUID организации; если задан — подставляется до подбора договора. С 1.0.6 |
| `contract_ref` | нет | UUID договора; если задан — подставляется явно (без автоподбора). С 1.0.5 |
| `date` | нет | Дата документа (ISO 8601). Если не указана — текущая дата сеанса |
| `comment` | нет | Комментарий документа |
| `files` | нет | Массив присоединяемых файлов |

**Контрагент:** нужен либо `contractor_ref`, либо `contractor` с хотя бы одним из полей `inn` / `name`.

Если переданы и ИНН, и наименование — применяются **оба** условия (логика И). Ищутся только элементы **без пометки удаления**.

### Поля строки `works[]`

| Поле | Обязательность | Описание |
|------|----------------|----------|
| `work_type` | условно | Наименование вида работы (`Справочник.эсВидыРаботСотрудников`, только действующие) |
| `work_type_ref` | условно | UUID вида работы; приоритетнее поиска по имени |
| `date` | нет | Дата выполнения работы. По умолчанию — начало дня даты документа |
| `time_start` | нет | Время начала (`HH:mm:ss` или ISO) |
| `time_end` | нет | Время окончания |
| `hours` | нет | Количество часов; используется, если не задан интервал или после его расчёта не применим |
| `description` | нет | Содержание работы (попадает в ТЧ **Работы** и в сводное описание файлов) |

**Вид работы:** для каждой строки нужен `work_type_ref` или `work_type`.

**Время и часы:**

- если указаны `time_start` и `time_end` — часы считаются через `эсРаботаСДатамиКлиентСервер.РазницаДат` (как на форме документа);
- иначе можно передать `hours` напрямую;
- после расчёта часов вызывается пересчёт сумм строки.

### Поля `files[]`

| Поле | Обязательность | Описание |
|------|----------------|----------|
| `name` | **обязательно** | Имя файла с расширением |
| `content_base64` | **обязательно** | Содержимое файла в Base64 |

Файлы привязываются к **документу** (каталог `эсЛистУчетаРабочегоВремениПрисоединенныеФайлы`).

**Описание каждого файла** (`Описание` в БСП) формируется как **склейка** всех непустых `works[].description` через перевод строки.

## Ответы

### 200 — успех

```json
{
  "name": "эсЛистУчетаРабочегоВремени",
  "ref": "a1b2c3d4-e5f6-...",
  "number": "00000012345",
  "date": "2025-06-19T10:00:00",
  "posted": false,
  "contractor_ref": "uuid-контрагента",
  "contract_ref": "uuid-договора",
  "works_count": 2,
  "files_count": 1
}
```

| Поле | Описание |
|------|----------|
| `ref` | UUID созданного документа |
| `contract_ref` | UUID договора, подобранного типовой логикой |
| `organization_ref` | UUID организации после подбора по контрагенту/договору |
| `posted` | всегда `false` (документ не проводится) |
| `works_count` | число строк в ТЧ **Работы** |
| `files_count` | число добавленных присоединённых файлов |

### 404 — не найдено

```json
{ "error": "contractor_not_found" }
```

```json
{ "error": "contractor_ref_not_found" }
```

```json
{ "error": "organization_not_found" }
```

```json
{ "error": "organization_ref_not_found" }
```

```json
{ "error": "contract_not_found" }
```

```json
{ "error": "contract_ref_not_found" }
```

```json
{ "error": "work_type_not_found", "work_index": 0 }
```

### 409 — неоднозначный поиск

```json
{
  "error": "ambiguous_contractor",
  "candidates": [
    { "ref": "uuid-1", "name": "ООО Ромашка", "inn": "7701234567" },
    { "ref": "uuid-2", "name": "ООО Ромашка (филиал)", "inn": "7701234567" }
  ]
}
```

```json
{
  "error": "ambiguous_work_type",
  "work_index": 1,
  "candidates": [
    { "ref": "uuid-1", "name": "Консультация" }
  ]
}
```

Повторите запрос с `contractor_ref` или `works[n].work_type_ref` из списка `candidates`.

### 400 — ошибка запроса или записи

Типичные причины:

- невалидный JSON;
- пустой или отсутствующий массив `works`;
- не задан контрагент;
- не заполнены константы `эсЛУРВ_ВидОценкиСМК` / `эсЛУРВ_ВидОценкиРезервноеКопирование`;
- ошибка проверки заполнения при записи документа;
- некорректный формат времени или файла.

Формат ответа: `{ "error": "текст ошибки" }`.

## Внутренняя логика (типовые модули ЭСТИ)

### 1. Значения по умолчанию

Вызывается `эсЗаполнениеОбъектовСервер.ЗаполнитьОбъектЗначениямиПоУмолчанию` — как в `ПриСозданииНаСервере` формы документа:

- вид цены, валюта, подразделение;
- учёт НДС, сумма включает НДС;
- **сотрудник** текущего пользователя;
- организация и прочие реквизиты по настройкам.

### 2. Контрагент и договор

После установки `Контрагент` вызывается:

```bsl
эсЗаполнениеОбъектовСервер.ПриИзмененииЗначенияКонтрагента(
    ДокументОбъект,
    "Организация, Контрагент, Партнер, Договор",
    "Покупатель");
```

Это повторяет логику обработчика `КонтрагентПриИзменении` на форме:

- синхронизация **Партнёр**;
- подбор **Договор** (основной договор контрагента, заключённые договоры на дату документа, вид «С покупателем»).

Затем `УстановитьФлагиЛУРВПоДоговору` (аналог `НаСервереУстановитьФлагиПоДоговору`):

- `РазрешитьУказыватьСтоимостьРабот`, `УказатьСтоимостьРабот`;
- `УчитыватьНДС`, `СуммаВключаетНДС`;
- `ВидЦены` из договора.

### 3. Оценки СМК и РК

Из констант:

- `эсЛУРВ_ВидОценкиСМК` → `ОценкаЗаполненияЛистаУчета`;
- `эсЛУРВ_ВидОценкиРезервноеКопирование` → `ОценкаОрганизацииРезервногоКопирования`.

Если константа не заполнена — ошибка 400 (как отказ формы при создании).

### 4. Заполнение строки работы

`ИнициализироватьНовуюСтрокуРаботыЛУРВ` повторяет `ПриНачалеРедактированияРабот` на форме, затем `ЗаполнитьСтрокуРаботыЛУРВ` — `РаботыВидРаботыПриИзменении`:

| Действие | Источник |
|----------|----------|
| **Замечания** | всегда `Замечаний нет` |
| Задание сотруднику, цены по договору | из шапки / договора (как на форме) |
| Содержание (если пусто) | реквизит вида работы `СодержаниеРаботы` |
| Место работы | `МестоВыполненияРаботы` или предопределённое «по умолчанию» |
| Количество выездов | из вида работы |
| Номенклатура, номенклатура выезда | из вида работы + расчёт цен/сумм |
| Количество часов | из интервала времени или из `hours` |

Расчёт сумм — `РассчитатьСтрокуРаботыЛУРВНаСервере` (обёртка: строка ТЧ → структура → `эсРаботаСТабличнымиЧастямиКлиентСервер.РассчитатьСтроку`).

### 5. Сотрудник и сдача листа

| Реквизит | Поведение API |
|----------|----------------|
| `Сотрудник` | по умолчанию — из типового заполнения (текущий пользователь); `employee_ref` / `employee.name` переопределяют |
| `ЛистУчетаСдан` | всегда `Истина` |
| `ДатаСдачи` | текущая дата сеанса, если пусто |
| `УстановитьВыполнениеЗаданийСотруднику` | `Истина`, если включена константа `эсУказыватьВариантЗакрытияЗаданияВДокументеЛУРВ` |

### 6. Запись документа

`ДокументОбъект.Записать(РежимЗаписиДокумента.Запись)`.

В `ПередЗаписью` объекта пересчитываются итоги часов/выездов документа и суммы (если указана стоимость).

### 7. Присоединённые файлы

Для каждого элемента `files[]`:

1. декодирование Base64 → `ДвоичныеДанные`;
2. помещение во временное хранилище;
3. `РаботаСФайлами.ДобавитьФайл` с владельцем = ссылка на ЛУРВ;
4. описание файла = сводка всех `description` из `works`.

## Ограничения и требования

| Тема | Детали |
|------|--------|
| Проведение | Документ **не проводится**; движения по регистрам не формируются |
| Права | Пользователь HTTP-сервиса должен иметь право на запись ЛУРВ и добавление присоединённых файлов (роль `LURV_HTTP_ОсновнаяРоль` (только Use на HTTP); запись объектов — через привилегированный режим) |
| Константы | В ИБ должны быть заполнены константы оценок СМК/РК |
| Поиск по имени | Подстрока с нормализацией; resolve — 200+`ambiguous`; create — 409+`candidates` |
| Универсальный API | `POST /document/эсЛистУчетаРабочегоВремени` не вызывает типовую логику ЭСТИ — для ЛУРВ используйте `/lurv` |

## Связанные объекты конфигурации

- Документ: `эсЛистУчетаРабочегоВремени`
- Справочники: `Контрагенты`, `ДоговорыКонтрагентов`, `эсВидыРаботСотрудников`, `эсМестаВыполненияРабот`
- Присоединённые файлы: `эсЛистУчетаРабочегоВремениПрисоединенныеФайлы`
- Типовые модули: `эсЗаполнениеОбъектовСервер`, `эсРаботаСДоговорамиСервер`, `эсРаботаСТабличнымиЧастямиКлиентСервер`, `РаботаСФайлами`

## Проверка после загрузки расширения

1. Загрузить расширение `ЛУРВ_HTTP` в тестовую ИБ.
2. Создать ЛУРВ через API и сравнить договор/реквизиты с ручным созданием на форме для того же контрагента.
3. Проверить ТЧ **Работы**: часы, номенклатура, место выполнения.
4. Проверить присоединённые файлы и их описание.
5. Убедиться, что документ записан и **не проведён**.
